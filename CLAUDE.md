# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo này

`OpenViCloud/titan-control-plane` là control plane của Titan (ASP.NET Core 9): REST API `/v1`, identity, tenancy, quota, billing, ví, và bảng lệnh `core.provider_commands` mà [`titan-incus-worker`](https://github.com/OpenViCloud/titan-incus-worker) lease qua `/internal`. Repo này chỉ chứa code, test, `api/openapi-v1.json` và CI của control plane. Gate "không phá `/v1`" là `.github/workflows/ci-api.yml`; repo CLI, provider và `titan-landing` chép spec từ repo này (`scripts/sync-spec.sh <sha>` của từng repo).

Doc ở lại repo `OpenViCloud/titan-ops` (private): luật kiến trúc (`docs/architecture/`), design + user story từng feature (`docs/features/`), hạ tầng, iteration, release, gitops và quy trình (skill `.claude/commands/`). Comment và file này nêu một doc của titan-ops bằng từ khoá `titan-ops <đường dẫn dưới docs/>#<anchor>` (`titan-ops architecture/code-comments.md#private-repo-refs`), không bằng URL: repo này public, link vào titan-ops là 404 với người ngoài; step CI "No URL into private titan-ops" đỏ khi có URL. Ngoại lệ: 41 đường dẫn `docs/…` (39 dòng) nằm trong **chuỗi** (thông điệp assert của guard, thông điệp health check và log, văn bản pháp lý `LegalDocumentCatalog`) giữ nguyên chữ, là đường dẫn trong repo titan-ops — đổi chuỗi là đổi hành vi (văn bản pháp lý đổi thì phải tăng `Version`). Iteration và release chạy từ phiên ở titan.

## control-plane Architecture

Clean Architecture: `Titan.Host` → `Titan.Application` → `Titan.Domain` ← `Titan.Infrastructure`

- `Titan.Host` — `Program.cs` only: DI registration, middleware pipeline, `app.Run()`. No business logic, no endpoints.
- `Titan.Application` — Services + DTOs. Provider commands are enqueued here (`IProviderCommandQueue`). **Validators do NOT live here** — xem mục dưới.
  - **Gốc `Titan.Application/` chỉ có 3 nhánh + 3 thư mục có tên** (`titan-ops architecture/code-structure.md#application-tree` · `titan-ops architecture/code-structure.md#services-branch`): `Commands/` · `Queries/` · `Services/` · `Abstractions/` · `Exceptions/` (exception của request: 400, 403, 503, Domain không ném) · `Options/`. Module (`Billing` · `Platform` · `Catalog` · `Compute` · `Networking` · `Admin`) là **segment thứ hai** của mỗi nhánh. Namespace khớp folder: `Titan.Application.Services.Billing.TopUp`, … Guard `ApplicationRoot_HoldsOnlyTheBranchesAndNamedFolders` đỏ khi một thư mục thứ bảy mọc ở gốc.
    - 🔑 **`Commands/` và `Queries/` là trục BẬC MỘT** (`titan-ops architecture/code-structure.md#application-tree` + `titan-ops architecture/code-structure.md#contracts`): `Commands/<Module>/<Aggregate>/` và `Queries/<Module>/<Aggregate>/`, contract trong `Contracts/` của **chính bên đó**. Handler `*CommandHandler`/`*QueryHandler` (**cả type lẫn tên file**), method luôn `HandleAsync`, **không** interface, DI thủ công từng dòng ở `Program.cs`. **Không** MediatR (`Send()` cắt go-to-definition = sai chính mục tiêu).

**Error response shape:** `{ status, title, code }` — error code (e.g. `VM_QUOTA_EXCEEDED`) is in `code`, not `detail`.

**Auth:** bearer `ovc_…` = token API của một member (scheme `ApiToken`, principal chỉ `sub`), bearer khác = JWT Keycloak (`titan-ops features/public-api/design.md#api-token`).

**Middleware pipeline:** `UseHttpMetrics` → endpoint restore → `UseExceptionHandler` → `UseCors` → `UseWebSockets` → `UseAuthentication` → `TenantResolutionMiddleware` → `UseAuthorization` → `RequestBodyLimitMiddleware` → `IdempotencyMiddleware` → `UseFastEndpoints`. `UseHttpMetrics` sits outside the exception handler so a request that throws is counted with the handler's code; the endpoint restore puts back the route the handler clears. `RequestBodyLimitMiddleware` nâng giới hạn body của Kestrel chỉ cho route mang metadata `RequestBodyLimit` (route upload code của function, `titan-ops features/ovc-function/design.md#code-storage`) và trả `413` với mã của route, trước khi `IdempotencyMiddleware` (người đọc body đầu tiên, băm theo luồng) chạm vào body. `/metrics` is served by a separate Kestrel server on `Metrics:Port`, none when unset. The tenant middleware resolves `TenantId` from DB (not JWT) and short-circuits with `403 TENANT_SUSPENDED` for write operations when tenant is suspended — a websocket upgrade (SSH session) counts as a write.

**FastEndpoints:** HTTP endpoints live in `Titan.Infrastructure/Endpoints/`. Base class is `Endpoint<TRequest, TResponse>` (or `EndpointWithoutRequest`). Route params bound via `Route<T>("paramName")`. Auth configured per-endpoint: `AllowAnonymous()`, `Roles("platform-admin")`, or default (requires auth). **Validators live HERE, next to their endpoint** — `class XValidator : Validator<XRequest>` cùng file endpoint hoặc file `*Validator.cs` cùng thư mục (FastEndpoints' `Validator<T>`, tự động discover, chạy trước `HandleAsync`). **Không có validator nào trong `Titan.Application`.** Validation errors return `{ status: 400, title, code: "VALIDATION_ERROR" }`.

**Test pattern — service-level, stub-first; doubles only in unit tests** (`titan-ops architecture/testing.md#doubles-only-in-unit-tests`, guard `DoublePlacementTests`): `Category=Integration` and `Category=FullHost` run real implementations — Postgres via `Titan.Tests/Infrastructure/Integration/TestPostgres.cs` (two FullHost cases run with no database on purpose: the 500 of `ExceptionLoggingHostTests` and of `MetricsHostTests`) — no Moq, no `Fakes/`, no InMemory, no replaced host service.
- Tests target the handlers directly (CQRS; the older `*ServiceTests` files keep their call shape through a small private facade over the real handlers) — no HTTP layer, no `WebApplicationFactory`.
- Prefer **stubs** (concrete class implementing interface, fixed return values, no call verification) over mocks.
- Use **Moq mocks** only when call verification is required (e.g. assert `IProviderCommandQueue.EnqueueVmCreateAsync` was called exactly once with specific args).
- Test files: `Titan.Tests/Services/*ServiceTests.cs`, `Titan.Tests/Auth/TenantResolutionMiddlewareTests.cs`.
- **Endpoint-level tests** — an endpoint that only forwards to a service needs no test of its own; the service test covers it. An endpoint that carries **its own logic** (parsing, composing, auth gating, enriching) gets one, using `FastEndpoints.Factory.Create<TEndpoint>(...)` — no host, no DB. Examples: `GetTenantBillingSummaryEndpointTests.cs`, `SyncTemplatesEndpointTests.cs`, `ObservationExistsRequiredTests.cs`.
  > This rule exists because of `BILL-01`: the billing summary endpoint held enrichment logic that 500'd for any tenant with ≥2 billed VMs, and service-level tests covered none of it. "Service-level only" is right for thin adapters and blind to everything else.
- **Full-host tests** (`WebApplicationFactory` through `Api/RealHostFactory.cs`: the host as `Program.cs` wires it, on its own migrated Postgres) stay reserved for cross-cutting concerns — `CorsTests.cs`, `HealthCheckTests.cs`, `OpenApiSpecTests.cs`, `CatalogContractTests.cs`.
- **Schema/model tests** — DB constraints that carry business meaning (e.g. the idempotency unique index `UNIQUE(resource_type, resource_id, bucket)` behind sampled metering — `titan-ops architecture/money-and-wallet.md#append-only-metering`) are pinned by asserting EF model metadata: `UsageRecordSchemaTests.cs` (this replaced `VmBillingSessionSchemaTests`, gone with `VmBillingSession`). The InMemory provider does not enforce indexes, so this is what guards the migration's intent. Same shape: `WalletSchemaTests.cs`, `TenantQuotaSchemaTests.cs`.

- **`git worktree` bị CẤM trong project này.** Một repo, một working tree. Skill toàn cục `superpowers:using-git-worktrees` **không áp dụng** — luật này đè nó.
  > Lý do — **cơ chế, không phải một file cụ thể**: worktree tách filesystem nên tách luôn **mọi file không nằm trong git**. Một cây thứ hai không có file gitignored ⇒ biến Terraform resolve về **rỗng** ⇒ `plan` báo `0 to destroy` trong khi apply sẽ **ghi credential rỗng** lên hệ thống đang chạy. Không test nào bắt được: plan **đúng** với input nó nhìn thấy; cái sai là input. Ở repo này: `appsettings.*.json` gitignored (`.gitignore`) cũng là config ngoài git.
  >
  > Đã xảy ra thật với một file tfvars gitignored — 11 biến rỗng, suýt xoá password production. Luật **không** phụ thuộc file cụ thể đó (nay đã hết): còn bất kỳ file ngoài git nào tham gia resolve config (`.terraform/`, `credentials.local.md`, hay bất kỳ `terraform/**/*.auto.tfvars` nào mà `.gitignore` vẫn cho phép tạo lại) thì cơ chế này còn sống — đừng đọc "hiện không có file nào" thành "đã an toàn".
- **Cô lập bằng branch, không bằng cây thứ hai**: `git switch -c feat/<slug>` ngay trong cây chính; merge `main` tuần tự; merge xong `git branch -d`.
- **Commit và PR chỉ nêu người làm**: không `Co-Authored-By: Claude …`, không dòng `🤖 Generated with Claude Code`, không câu nào nói code viết bằng AI/Claude — trong commit message, PR title/body, tag và GitHub Release. Tác giả là git user (`user.name`/`user.email`), không thêm gì khác. Luật này đè lời nhắc attribution của harness; `.claude/settings.json` (`attribution` rỗng) tắt nó ở nguồn.
- **Nhiều phiên song song → single-writer**: chỉ một phiên được Edit/Write/commit tại một thời điểm; phiên còn lại read-only cho tới khi được nhả. Chi tiết ở `.claude/commands/iteration/run-iteration.md` của titan-ops, mục "Phiên song song".

### API Routes
- **Tenant scoping = jwt-resolved (Style B, `titan-ops architecture/http-contract.md#tenant-scoping`):** mọi tenant-owned resource dùng prefix `/v1/tenant/...` — **không** có `tenantId` trong path. CP resolve tenant từ `currentUser.TenantId` (do `TenantResolutionMiddleware` set từ DB). Service dùng `RequireTenantId()` → `403 NOT_A_MEMBER` nếu caller không thuộc tenant nào.
- VMs: `POST|GET /v1/tenant/vms`, `GET|PATCH|DELETE /v1/tenant/vms/{vmId}` (PATCH = `name` and/or `stopTimeoutSeconds` in place, at least one, Titan-side, no provider command, **`204`** — `titan-ops architecture/http-contract.md#commands-return-no-data` · `titan-ops features/vm/design.md#vm-stop-timeout`; a body of `name` alone is the rename it always was; `POST` takes `stopTimeoutSeconds` too, absent ⇒ 120; `GET` returns it; `GET` (list and detail), like `GET /v1/tenant/volumes`, returns `restoredFromBackup`: `true` for a VM or volume an admin restored from a backup, which does not count toward quota — `titan-ops features/backup/design.md#restore-as-new-resource`)
- SSH session: `GET /v1/tenant/vms/{vmId}/ssh` — **websocket**, JWT or API token on the upgrade, out of OpenAPI; CP runs `nc -N 127.0.0.1 22` in the guest via Incus exec and relays bytes; 5 sessions/tenant, one row each in `core.shell_sessions` (every replica counts the same); 30 min idle ⇒ closed (`titan-ops features/vm/design.md#ssh-session`). One of the two places CP talks to Incus besides reads, with the console below (`titan-ops architecture/provider-and-worker.md#only-the-worker-acts-on-the-provider`). CLI `openvicloud vm ssh`
- Console: `POST /v1/tenant/vms/{vmId}/console-tickets` `{ticket}` ⇒ `204` (client-made `ovct_` ticket, only its SHA-256 kept 30 s in `core.console_tickets`), then `GET /v1/tenant/vms/{vmId}/console?ticket=` — **websocket**, AllowAnonymous (the ticket, taken once by `DELETE … RETURNING`, stands for the token a browser cannot send; the request then runs as the ticket's taker); CP attaches the VM's serial console (`POST /1.0/instances/{name}/console`, no force) and relays bytes; resize as a JSON text frame; shares the 5-session limit; refusals after the upgrade close with `4000 + status`, reason = code (`titan-ops features/vm/design.md#vm-console`).
- VM metrics (`titan-ops features/vm/design.md#vm-metrics`): `GET /v1/tenant/vms/{vmId}/metrics?range=1h|24h|7d` (vắng ⇒ `1h`, chữ khác ⇒ `400 VALIDATION_ERROR`, VM tenant khác ⇒ `404 VM_NOT_FOUND`; điểm tính ở `Queries/Compute/Vm/VmMetricPoints`, hàm thuần) đọc `core.vm_metric_samples` (bảng, không aggregate: `Persistence/VmMetricSample`, port `IVmMetricStore`); worker ghi qua `POST /internal/clusters/{clusterId}/vm-metrics` (`X-Internal-Token`, `204`; tên instance không VM nào của cluster mang ⇒ bỏ, `(vm, sampledAt)` đã có ⇒ bỏ; không đổi status nào); job `Hosting/VmMetricRetention` (`vm-metric-retention`) xoá mẫu quá `VmMetricRetention:RetentionDays` (7); job `Hosting/UsageRecordRetention` (`usage-record-retention`) xoá `core.usage_records` có `bucket` trước `UsageRecord.KeptFrom(now)` (`KeptDays` = 90, hằng, không option); cả hai chạy mỗi giờ khi CronJob gọi (`titan-ops architecture/background-jobs.md#background-jobs`) — `titan-ops features/billing/metering/design.md#usage-retention`
- VM Snapshots: `POST|GET /v1/tenant/vms/{vmId}/snapshots`, `POST /v1/tenant/vms/{vmId}/snapshots/{snapshotId}/revert`, `DELETE /v1/tenant/vms/{vmId}/snapshots/{snapshotId}` — **`{vmId}` bắt buộc ở mọi route snapshot**
- VM key additions (`titan-ops features/vm/design.md#vm-key-addition`): `POST|GET /v1/tenant/vms/{vmId}/key-additions` (`POST` nhận `sshKeyIds`, 1–10 id khác nhau, trùng gộp một, `400 VALIDATION_ERROR` ngoài khoảng; `Idempotency-Key` bắt buộc; VM không `Running` hay một key addition khác còn `Adding` ⇒ `422 VM_INVALID_STATUS`, không tạo hàng, không gửi lệnh; id không phải key của tenant ⇒ `404 SSH_KEY_NOT_FOUND`), `GET .../{keyAdditionId}` — **`{vmId}` bắt buộc ở mọi route**; child entity của `Vm` (`VmKeyAddition`, trạng thái `Adding`/`Added`/`Failed`, không `Operation`/`MarkObserved`/`MarkNotFound` như tám loại trên provider: không có gì để quan sát sau báo cáo); lệnh `vm-key-addition.create`, khoá `vm-key-addition-create-{keyAdditionId}-{requestId}`, payload mang `keyLines` dựng lại từ key đã parse (như `vendorData` của `vm.create` dưới, không bao giờ chữ khách gửi thẳng).
- Volumes: `POST|GET /v1/tenant/volumes`, `DELETE /v1/tenant/volumes/{volumeId}`, `POST .../{volumeId}/attach|detach`, `POST|GET .../{volumeId}/snapshots`, `POST /v1/tenant/volumes/{volumeId}/snapshots/{snapshotId}/restore`, `DELETE /v1/tenant/volumes/{volumeId}/snapshots/{snapshotId}` — **`{volumeId}` bắt buộc ở mọi route snapshot**
- Networks: `POST|GET|DELETE /v1/tenant/networks` (`POST` nhận `enablePublicIpv6` — IPv6 public **theo network**, một `/64` của cluster, `titan-ops features/network/design.md#ipv6-public`), firewall rules `/v1/tenant/networks/{networkId}/firewall-rules`
- Load balancers: `POST|GET /v1/tenant/load-balancers`, `GET|PUT|PATCH|DELETE /v1/tenant/load-balancers/{loadBalancerId}` (`PATCH` = đổi tên, chỉ phía Titan, VIP giữ — `titan-ops features/load-balancer/design.md#lb-rename`) — L4 TCP/UDP trên OVN load balancer của Incus, chỉ network đã bật IPv6 public; VIP `<64 của network>::1:n` do Titan cấp; `PUT` = cả cấu hình (listener + backend VM), `204`; miễn phí, quota `MaxLoadBalancers` (`titan-ops features/load-balancer/design.md#vip-in-network-64`)
- API tokens: `POST|GET /v1/tenant/api-tokens`, `DELETE /v1/tenant/api-tokens/{apiTokenId}` — portal sinh bí mật `ovc_…`, control plane chỉ lưu SHA-256; tối đa 20/tenant (hằng số, không quota); xoá cứng; CLI đọc `OPENVICLOUD_TOKEN` (`titan-ops features/public-api/design.md#api-token`)
- Functions (`titan-ops features/ovc-function/design.md#function-lifecycle`): `POST|GET /v1/tenant/functions` (`POST` `{name, clusterId}` ⇒ `201 {functionId}`; `clusterId` phải là cụm function của `FunctionClusters__*`, không thì `404 CLUSTER_NOT_FOUND` — prd không khai cụm function nên tạo luôn `404`; tối đa 20/tenant, hằng `Function.MaxPerTenant` qua `TenantQuotaGate.EnsureFunctionRoom`, không quota; function đang xoá vẫn tính tới khi `Deleted`), `GET|DELETE /v1/tenant/functions/{functionId}` (`GET` `{id, name, clusterId, status, url, runningVersionId, deployingVersionId, requestFailureReason, requestFailedAt, createdAt}`, `url` = `FunctionUrl:Scheme://<externalId>.FunctionUrl:Domain`, null tới deploy đầu, hay khi không khai `FunctionUrl:Domain`; `DELETE` ⇒ `202`, cả khi xoá tại chỗ), `POST|GET /v1/tenant/functions/{functionId}/versions` (`POST` `multipart/form-data` hai phần `config` JSON `{runtime, handler?, memoryMiB?, timeoutSeconds?}` + `code` zip ⇒ `201 {versionId}`; phần `code` quá 50 MiB ⇒ `413 FUNCTION_CODE_TOO_LARGE` lúc byte thứ 50 MiB + 1 tới, route nâng giới hạn body riêng của nó lên 51 MiB (`RequestBodyLimit`); zip ra file tạm của request, không mảng byte; `GET` chỉ phiên bản còn giữ, mới nhất trước), `POST /v1/tenant/functions/{functionId}/deploy` `{versionId}` ⇒ `202`. Phần `config` của upload nhận thêm `env` (object tên → chuỗi), `secrets` (object tên biến → `{secret: tên, version: "latest" | số ≥ 1}`) và `schedule` (5 trường cron UTC, tuỳ chọn) (`titan-ops features/ovc-function/design.md#function-config`): tên biến theo luật tên secret dưới, tên dành riêng (`TITAN_*`, `PORT`, `K_SERVICE`, `K_REVISION`, `K_CONFIGURATION`), một tên ở cả hai, lịch không đúng 5 trường (phút 0-59, giờ 0-23, ngày 1-31, tháng 1-12, thứ 0-6 (API `CronJob` từ chối 7); mỗi trường `*` hay danh sách số/khoảng, `/bước` tuỳ chọn; không tên, không macro; `Function.IsASchedule`, bộ đọc riêng, không thư viện cron), hay tổng byte UTF-8 của tên + giá trị biến + tên biến secret + `ValueBytes` của từng phiên bản secret quá 8192 (`Function.MaxConfigBytes`; validator đo phần biết được, handler cộng `ValueBytes`) ⇒ `400 VALIDATION_ERROR`; handler giải từng secret **trước** khi ghi zip hay push image: tên không có trong tenant hay số không còn giữ ⇒ `422 FUNCTION_SECRET_NOT_FOUND`, không ghi gì; `latest` chốt thành số lúc upload. `GET …/versions` trả thêm `env` nguyên văn, `secrets` tên biến → `{secret, version}` (không giá trị), `schedule`. Deploy: mọi secret phiên bản trỏ tới còn đúng số đó ⇒ không thì `422 FUNCTION_SECRET_NOT_FOUND`, không lệnh
- Function secrets (`titan-ops features/ovc-function/design.md#function-secrets`): `POST /v1/tenant/function-secrets` `{name, value}` ⇒ `201 {name, version: 1}`, `POST /v1/tenant/function-secrets/{name}/versions` `{value}` ⇒ `201 {version}` (giá trị mới = phiên bản mới, không PUT; khoá hàng secret trước khi chọn số), cả hai `Idempotency-Key` bắt buộc; `GET /v1/tenant/function-secrets` (theo tên: `name, createdAt, latestVersion, versions [{version, createdAt}] mới nhất trước, usedBy [{functionId, functionName, versionId, versionNumber, secretVersion, running}]` từ phiên bản còn giữ của function chưa `Deleted`; **không bao giờ** giá trị hay bản mã); `DELETE /v1/tenant/function-secrets/{name}` ⇒ `204`, xoá cứng cả phiên bản; phiên bản đang chạy hay đang deploy của một function chưa `Deleted` trỏ tới ⇒ `409 FUNCTION_SECRET_IN_USE` nêu tên function. Tên `^[A-Za-z_][A-Za-z0-9_]*$` ≤ 128, duy nhất trong tenant (`409 FUNCTION_SECRET_EXISTS`); giá trị 1–4096 byte UTF-8; tối đa 50/tenant qua `TenantQuotaGate.EnsureFunctionSecretRoom` (`422 FUNCTION_SECRET_QUOTA_EXCEEDED`, hằng `FunctionSecret.MaxPerTenant`, không quota); tên lạ hay của tenant khác ⇒ `404 FUNCTION_SECRET_NOT_FOUND`. Giá trị không vào log, response, activity (`ToString` của command che `Value`); activity `function_secret.{create_requested,created,version_add_requested,version_added,delete_requested,deleted}` (`Stage` + `StageOutcome` cùng lần lưu, như SSH key), resource `function_secret`, id + tên secret
- SSH keys: `POST|GET /v1/tenant/ssh-keys`, `DELETE /v1/tenant/ssh-keys/{sshKeyId}` — chỉ ở Titan, xoá cứng; tạo VM chọn key qua `sshKeyIds` ⇒ control plane dựng cloud-init vendor-data (boothook ghi config `AuthorizedKeysFile` một lần mỗi instance cho MỌI VM, kể cả không key, để key thêm sau (xem VM key additions trên) có sẵn chỗ ghi; key nếu có vào `/etc/ssh/openvicloud/ubuntu`), lệnh `vm.create` mang `vendorData` không bao giờ null (`titan-ops features/vm/design.md#ssh-key`); `consolePassword` (12–72 ký tự) chỉ đi dưới dạng hash SHA-512 crypt trong cùng boothook, một script per-instance chạy `chpasswd -e` (`titan-ops features/vm/design.md#console-password`); body của Idempotency băm HMAC dưới `Idempotency:HashKey`, thiếu khoá ⇒ không khởi động (`titan-ops architecture/http-contract.md#idempotency-key`)
- Billing (tenant): `GET /v1/tenant/billing/summary`, `GET /v1/tenant/vms/{vmId}/cost` (cả hai, như `POST /internal/billing/invoices/run`: năm ngoài 1–9999 hay tháng ngoài 1–12 ⇒ `400`; ngày đầu tháng trước `now − 90 ngày` ⇒ `422 USAGE_PERIOD_EXPIRED`), `GET /v1/tenant/billing/invoices[/{invoiceId}]`, **`POST /v1/tenant/billing/invoices/{invoiceId}/pay`** (trả hoá đơn từ ví — `titan-ops architecture/money-and-wallet.md#human-confirmed-debit`)
- Admin (platform-admin, **không** thuộc public contract): `GET /v1/tenants`, `PATCH /v1/tenants/{tenantId}/status`, `PATCH /v1/tenants/{tenantId}/debt-ceiling`, `GET /v1/admin/billing/receivables`, `PATCH /v1/admin/vm-offerings/{offeringId}/price`, `PATCH /v1/admin/invoices/{invoiceId}/pay` (**`MarkPaid` — tiền đến NGOÀI Titan, không đụng ví**), **`POST /v1/admin/invoices/{invoiceId}/settle-from-wallet`** (**trừ ví của tenant, bấm hộ khách** — `titan-ops architecture/money-and-wallet.md#human-confirmed-debit`), `GET /v1/admin/function-runtimes` và `POST /v1/admin/function-runtimes/sync` (`202`; mục Function runtime dưới). ⚠️ Hai route cuối **cố ý khác nhau**; gộp chúng là làm audit log mất khả năng phân biệt ai tiêu tiền của ai
- Admin khôi phục một backup (`titan-ops features/backup/design.md#restore-as-new-resource`): `POST /v1/admin/backups/vms/{vmId}/restore` và `POST /v1/admin/backups/volumes/{volumeId}/restore`, body `{backupKey, name}`, `Idempotency-Key` bắt buộc, `202` chỉ mang id mới (`{newVmId}` / `{newVolumeId}`). Id trên route là **nguồn**; kết quả là một VM hay volume **mới** của chính tenant đó, hàng `RestoredFromBackup` (không quota, không tính tiền), chờ create như mọi hàng mới: worker import archive dưới tên của hàng mới và báo qua route create sẵn có (`PATCH /internal/vms/{id}/requests/{requestId}`, `…/volumes/{id}/requests/{requestId}`; `Done` của VM mang `observed.status = Stopped` ⇒ VM nghỉ ở `Stopped`, `Done` của volume không mang `observed` ⇒ `Available`, `DesiredAttachedVmId` giữ nguyên). Ghi xuyên tenant như `DELETE /v1/admin/vms/{vmId}`: handler riêng ở `Commands/Admin/Backup/`, chủ đọc từ hàng nguồn, **không** `RequireTenantId`, **không** `TenantQuotaGate`, **không** `IActivityRecorder.Stage` (nó ghi dưới tenant của chính admin; `vm.created`/`volume.created` vào feed của chủ từ báo cáo create), không repository Catalog (offering và template chép từ hàng nguồn); mỗi hàng mới một dòng log và một dòng `AdminAuditLog` (`vm.restore.cross_tenant` / `volume.restore.cross_tenant`, `resource_id` = hàng mới, `owner_tenant_id` = tenant của nguồn, `detail` = `source=<id nguồn> backup=<backupKey>`), cùng một lần lưu với hàng mới và lệnh của nó. Thứ tự kiểm, không tạo gì trước khi mọi kiểm qua: tên (`ComputeInput.EnsureVmName`/`EnsureVolumeName`) → khoá hàng nguồn, vắng hay `Deleted` ⇒ `404 VM_NOT_FOUND`/`VOLUME_NOT_FOUND` → archive `Complete` của chính nguồn mang đúng `backupKey` (`IBackupRecordRepository.ListAsync`) ⇒ không có `404 BACKUP_NOT_FOUND` → (VM) tên còn rảnh trong tenant của chủ ⇒ `409 VM_NAME_TAKEN` → (VM) mỗi volume Incus đang giữ gắn vào nó (`CurrentAttachedVmId`, đọc bằng `ListAttachedToVmLockedAsync`) lấy archive `Complete` của chính nó **gần archive của VM nhất** (trước hay sau; bằng nhau ⇒ bản sớm hơn; đúng 24 giờ còn nhận), không có hay xa hơn 24 giờ ⇒ `422 BACKUP_OF_ATTACHED_VOLUME_NOT_FOUND` nêu tên và id volume (luật ở `Services/Admin/Backup/RestoreArchives`, hàm thuần) → factory `Vm.RestoreFromBackup`/`Volume.RestoreFromBackup` (`422 BACKUP_SOURCE_INVALID_STATE`); bản sao volume giữ tên volume nguồn và mang `DesiredAttachedVmId` = VM mới. Validator: `backupKey` khớp `IncusBackupKey.BackupKeyPattern` (`^[0-9]{8}T[0-9]{6}Z\z`: chỉ chữ số ASCII, không xuống dòng cuối — worker ghép nó lại vào khoá object), `name` như validator create của VM / volume ⇒ `400 VALIDATION_ERROR`. - Template mỗi cluster (giai đoạn 5): `template-sync-{templateId}-{clusterId}-{requestId}` — một hàng mỗi yêu cầu sync của một cluster; payload mang `requestId`. Trước đó: `template-sync-{templateId}-{clusterId}` (gửi lại mỗi sync-all)
- Runtime function mỗi cụm function: kind `function-runtime.sync`, khoá `function-runtime-sync-{runtimeId}-{clusterId}-{requestId}`, payload đúng `{runtimeId, requestId, name, image}` (`OpenViCloud/titan-function-worker:resource/runtime/sync.go`), không tenant, `cluster_id` = cụm function (`titan-ops features/ovc-function/design.md#function-lifecycle`; chỉ worker function lease kind `function.*`/`function-runtime.*`, job CI `worker-kinds` chạy guard route của cả hai worker — `titan-ops architecture/provider-commands.md#provider-command-table`)
- Function: kind `function.deploy` và `function.delete`, khoá `function-deploy-{functionId}-{requestId}` / `function-delete-{functionId}-{requestId}`, `cluster_id` = cụm function của function, `tenant_id` = tenant, `resource_id` = function; payload deploy đúng `{functionId, requestId, tenantId, versionId, image, handler ("" cho Go), memoryMiB, cpu, timeoutSeconds, maxInstances, concurrency, tenantQuota: {memoryMiB, pods, services, cronJobs}, containerLimits: {defaultMemoryMiB, maxMemoryMiB, defaultCpu, maxCpu}, env ({} khi không có), secrets ([{envName, secretId, version}], [] khi không có; không giá trị, không tên secret), schedule ("" khi không có)}`, payload delete đúng `{functionId, requestId, tenantId}` (`OpenViCloud/titan-function-worker:resource/function/`; `titan-ops features/ovc-function/design.md#function-lifecycle`). Hai kind nằm trong `ProviderCommandKinds.Function`: cột `lane` = `function` (migration `Functions`), nên lệnh function của một tenant không giữ lệnh Incus của tenant đó và ngược lại (`ProviderCommand.HoldsTheLaneOf`, `ListClaimableAsync`)
- VM snapshot (giai đoạn 4): `vm-snapshot-{create,revert,delete}-{snapshotId}-{requestId}`; payload mang `requestId`. Trước đó: `vm-snapshot-{kind}-{snapshotId}` (revert, delete từ chối hàng mở ⇒ `409`)
- Load balancer (giai đoạn 5): `load-balancer-{create,update,delete}-{id}-{requestId}`; payload mang `requestId`. Trước đó: `load-balancer-create-{id}`, `load-balancer-update-{id}-{intentId}`, `load-balancer-delete-{id}` (từ chối hàng mở ⇒ `409`)
- `vm-backup-{vmId}-{yyyyMMdd}`, `volume-backup-{volumeId}-{yyyyMMdd}` (ngày UTC, chữ số Gregorian): một bản mỗi ngày, lịch hỏi mỗi giờ — bản đã chạy (`Done`) nuốt lần hỏi, bản `Failed` chạy lại (`titan-ops features/backup/design.md#incus-backup`); `cluster-backup-{clusterId}-{yyyyMMdd}` (kind `cluster.backup`, không tenant, không tài nguyên) xếp khi mọi backup đĩa trong ngày của cluster đó đã `Done` hay `Failed`, và xếp thêm khoá `cluster-backup-{clusterId}-{yyyyMMddHH}` (`BackupCommandKeys.ClusterAgain`, giờ UTC) khi mọi backup đĩa đã kết thúc, không config nào của ngày còn chạy và một hàng backup đĩa tạo sau config `Done` mới nhất của ngày (`titan-ops features/backup/design.md#cluster-backup`); `restore-drill-{clusterId}-{yyyyMMdd}` (kind `restore.drill`, không tenant, không tài nguyên; payload `kind`, `resourceId`, `externalId`, `name`, `projectName`, `tenantId`) xếp một lần mỗi ngày mỗi cluster khi mọi backup đĩa đã kết thúc và bật `RestoreDrill:Enabled` — hàng `Failed` **không** mở lại trong ngày, khác backup đĩa (`titan-ops features/backup/design.md#restore-drill`). Khoá dựng ở `BackupCommandKeys`
- Restore một backup của admin (`titan-ops features/backup/design.md#restore-as-new-resource`): kind `vm.restore` khoá như create của VM **mới** (`vm-create-{newVmId}-{requestId}`), kind `volume.restore` khoá như create của volume **mới** (`volume-create-{newVolumeId}-{requestId}`), `requestId` = `Operation.PendingId` của hàng mới, nên `PendingRequestReader` nối được yêu cầu create đang chờ với hàng lệnh của nó. Hàng lệnh **không tenant** (như `restore.drill`), cluster của nguồn, `resource_id` = hàng **mới**. Không tenant vì worker lease hai kind này ở vòng của `restore.drill`, không ở vòng lệnh của khách: hàng có tenant nằm trong làn `command` của tenant đó, vòng lệnh của khách sẽ cứ chọn một lệnh của tenant ấy rồi vấp index unique của làn. Không tenant thì luật của `restore.drill` áp nguyên: trong ba kind đó mỗi lúc một hàng `Leased`, restore chờ drill và drill chờ restore (`ListClaimableAsync` so `tenant_id` và phía backup trong các kind được hỏi); không giữ lại lệnh của khách hay backup nào. Hai kind **không** thuộc `ProviderCommandKinds.Backup` ⇒ cột `lane` không đổi, không migration. Payload `volume.restore`: `newVolumeId`, `requestId`, `name`, `sourceVolumeId`, `backupKey`, `tenantId`, `projectName`, `sizeGb`. Payload `vm.restore`: `vmId` (VM **mới**), `requestId`, `name`, `sourceVmId`, `backupKey`, `tenantId`, `projectName`, `diskSizeGb`, `volumes` = `[{sourceVolumeId, newVolumeId, requestId}]` (mảng rỗng khi VM không có volume; `requestId` của mỗi phần tử là create của bản sao đó, đúng id lệnh `volume.restore` của nó mang — worker nhờ nó phân biệt bản sao đã restore xong với bản đang restore). `tenantId` viết đúng như payload `vm.backup`/`volume.backup`: worker dựng lại khoá object `incus/<cluster>/<tenantId>/<vms|volumes>/<id nguồn>/<backupKey>.tar.gz`. Restore VM xếp mọi `volume.restore` **trước** `vm.restore` (lease giao hàng cũ nhất trước), mỗi volume với `backupKey` của archive gần nhất của chính nó. `IProviderCommandQueue.EnqueueVolumeRestoreAsync`/`EnqueueVmRestoreAsync` (record `VolumeRestoredWithItsVm`). Guard: `ProviderCommandQueueTests` (bảng tenant, bảng resource, `EveryKind_CarriesExactlyTheFieldsTheWorkerReads`), `RequestLifecycleShapeTests` (`EveryVmCommandPayload_…`/`EveryVolumeCommandPayload_CarriesTheRequestId` đếm cả hai method, `EveryRestoreFromBackupHandler_LocksItsSource`), `ProviderCommandRepositoryStateTests` và `ProviderCommandLeaseDbTests` (làn)
- 🔑 **Một lệnh mỗi tài nguyên** (`titan-ops features/provider/design.md#tenant-lane`): cột `resource_id` (VM hay volume mà lệnh tác động; `volume-snapshot.restore` là volume nguồn; `vm.restore` và `volume.restore` là VM hay volume **mới**; `function.deploy`/`function.delete` là function; null cho network, rule, load balancer, template, runtime function, `cluster.backup`, `restore.drill`); lease không giao lệnh của một tài nguyên khi lệnh khác của nó đang `Leased`, ở bất kỳ làn nào, nên lệnh của khách chờ backup của chính tài nguyên đó và ngược lại; index unique `IX_provider_commands_resource_id_leased`. Yêu cầu đang chờ như thế không tính là kẹt (`PendingRequestReader`)

### DB Migrations
- Chạy qua `Titan.Infrastructure`, không dùng `Database.EnsureCreated()` hay auto-migrate
- 🔑 **Lịch sử migration bắt đầu ở `Initial`** (INCUS-STATUS PR-4: 59 migration gộp thành một, database `titan` của mọi env lúc đó xoá và dựng lại từ rỗng — `titan-ops architecture/code-structure.md#migrations`). Migration mới nối sau `Initial`; schema của `Initial` = schema của 59 migration (diff `pg_dump --schema-only` chỉ khác 15 `DEFAULT` backfill). Test migration theo dữ liệu cũ (21 file `*MigrationTests`) **đã gỡ**; `InitialMigrationTests` canh lịch sử bắt đầu ở `Initial` (một hàng `Initial`, đứng đầu) + seed catalog
- Network unique index có `HasFilter("status <> 'Deleted'")` (NETWORK-AGGREGATE-CLEAN; trước đó `current_existence`) — tenant có thể tạo lại network cùng tên sau khi xóa; **cùng** điều kiện với `NetworkRepository.ExistsByNameAsync`
- VM unique `(tenant_id, name)` có `HasFilter("status <> 'Deleted'")` (VM-SINGLE-STATUS; trước đó `current_existence <> 'Deleted'`) — **cùng** điều kiện với `VmRepository.ExistsByNameAsync`; index chặt hơn check thì tên handler cho là rảnh sẽ nổ `500` ở index

### Validation Limits
- Tên: VM 1–64 chữ, số, `-`, bắt đầu bằng chữ hoặc số (RFC 952 hostname); volume và snapshot 1–100, không chỉ khoảng trắng; load balancer và function 1–100 chữ, số, `-`, `_`, bắt đầu bằng chữ hoặc số. Function: bộ nhớ 128–2048 MiB bước 128, timeout 1–300 giây (`Function.IsAMemorySize`/`IsATimeout`, validator của phần `config` khi upload), handler `module.function`. Thời gian dừng VM 30–1800 giây, mặc định 120 (`titan-ops features/vm/design.md#vm-stop-timeout`). Command handler kiểm (`ComputeInput.Ensure*`; luật là `public static bool` và hằng `NameMaxLength`, `NamePattern`, `MinStopTimeoutSeconds`/`MaxStopTimeoutSeconds` của type), validator đọc hằng (và static property của child) và trả 400 trước; portal chặn 64 cho VM
- Network name: max 100 chars
